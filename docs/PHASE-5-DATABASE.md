# Phase 5: database audit and recovery runbook

**Authority:** This runbook supersedes legacy cPanel, backup, restore and rollback commands in `docs/deliverables/` and `worklog.md`. They are historical references, not instructions. The legacy `scripts/backup.sh`, `scripts/restore.sh` and `scripts/deploy-cyberpanel.sh` now fail closed; the cron HTTP endpoint does not make backups. Do not run this runbook against a live target without the specific approval stated below. No staging/production database, backup or service was accessed for this audit.

Compare verified environment IDs before each command. Use a read-only identity for auditing, least privilege for runtime, distinct migration grants, and separate disposable restore credentials. ## Read-only checks and observed drift

- Validate both schemata and run `node tests/migrations/client-parity.mjs sqlite` (or `mysql` after the corresponding generation). Both providers have **109 models and zero Prisma enums**. Role, state and status values remain application strings; database structural validation does not prove their allowed values.
- On a disposable target, or with explicit read-only authorization and an approved window, inject `DATABASE_URL` and run `npm run db:verify -- --approved-read-only`. It reports counts, a schema fingerprint, integrity, orphans and migration SHA-256 ledger mismatches. It does not print row values. For a pre-upgrade snapshot, pending entries are expected and make this strict post-migration command nonzero; compare them with the approved SQL list. A missing/failed/altered/unexpected migration is not an acceptable pending entry. Use `migrate status` and Prisma 7 `migrate diff --from-config-datasource --to-schema <matching-schema> --exit-code` with the matching config. Exit `2` from diff means drift; never execute its suggested script automatically.
- SQLite full scans run inside a read snapshot. MariaDB catalog scans and `CHECK TABLE` can be expensive; use a quiet or isolated copy with no concurrent DDL, with enough time/storage and catalog privileges. Counts and FK checks use one consistent read snapshot on transactional tables. `CHECK TABLE` and metadata/ledger queries are separate; the command is not an atomic inspection across concurrent DDL. Do not run structural scans against a busy live DB without the owner's approval. Compare metadata manifests privately when the digest differs; cross-provider fingerprints are not directly comparable.
- **Confirmed SQLite drift:** Prisma's read-only diff on nine replayed migrations requests rebuilding **25 tables**. A `PRAGMA table_info` comparison of the proposed definitions showed defaults differing: 16 tables differ on at least one Prisma empty-string default; eight education tables (`EnglishLearningCourse`, `EnglishLearningTutor`, `HigherStudyCourse`, `HigherStudyResearchProject`, `HigherStudyResource`, `HigherStudyScholarship`, `HigherStudySupervisor`, `HigherStudyUniversity`) have historical DB `verificationStatus='verified'` vs Prisma `'pending-review'`; `SocialAutomationState.id` has no DB default vs Prisma `'global'`. All 109 table and scalar-column names matched in replay. Direct SQL writers are not equivalent to Prisma writes. Require explicit review state in imports; do not trust historical defaults as approval. Do not apply the generated rebuilds, edit applied migration files or rewrite existing verification status in this PR. Reconcile defaults and check direct writers separately, rehearse copy/rebuild semantics if needed, and require authorization before serving or migrating an affected live DB.
- SQL FKs only check declared relationships, not logical bindings (tenant membership, polymorphic owner IDs, identity linkage, status values, or normalized business duplicates). Obtain approved aggregate counts and domain-specific invariants for customers, staff/admins, sessions, messages, audit/retention history, etc.; have app owners review exceptions before any correction. Keep identifiers and counts private where sensitive.

## Backup and isolated restoration

1. Get explicit backup approval. Verify out-of-band target identity, capacity, private directory/permissions (`umask 077`), encryption/access, RPO/RTO and scheduled retention with the owner. Use a new timestamped output prefix. Capture backup digest and restricted inventory in the change record. A release directory or repo checkout is not backup storage. The scripts do not schedule backups, implement offsite storage or delete backups. No live retention or ownership was verified.
2. Run `npm run db:backup -- /private/backups/unique-prefix --approved` with explicit approved source. SQLite uses the online backup API (including committed WAL data) and checks the snapshot. `npm run db:restore -- /private/backups/unique-prefix.sqlite` only restores into a new private temp directory, validates counts/schema/FKs/indexes, and prints its path. Handle the restored file like production data and remove it under the approved disposal policy. It never replaces the live DB.
3. MariaDB needs the `mariadb` and matching `mariadb-dump` clients. Set `BACKUP_VERIFY_DATABASE_URL` to a **new, empty**, operator-provisioned `alaminn_backup_verify_*` database with an independent account granted on only that exact schema, no GRANT OPTION and no roles/global data rights. Escape every underscore in the schema-level `GRANT` pattern (for example `` ON `alaminn\_backup\_verify\_ci`.* ``) to avoid wildcard privileges. Prefer a separate scratch server; a writable scratch schema on the production cluster requires its own approval. The script checks grants/emptiness, streams a gzip dump and restores only to that target. It compares source and restored table/column/index/FK/check metadata, runs integrity/orphan checks, then atomically publishes a private artifact without replacing an existing one. It does not delete scratch databases. On a quiescent source, compare **per-table** counts privately; independently counting a busy source does not certify the dump snapshot. For views, triggers/routines, nontransactional tables, database flags and operational grants, obtain separate backup/restore evidence; a Prisma table snapshot is not a complete server backup. Encrypt/transfer only under your retention policy.
4. If a check fails, stop. Keep the current service and original DB intact; mark an incomplete scratch target unsafe, preserve restricted diagnostics, then request a *new* scratch database. Do not use `--force`, disable checks, truncate scratch or restore over the live DB using these scripts.

## Migration and rollback decision tree

- Record exact source HEAD and current artifact; list each pending migration from the actual ledger on an approved read-only account and compare schema against the **currently deployed** client. Archive schema fingerprint/checksums and confirm the migration plan reviewed against a restored copy with representative data. No migration is added or applied to production by Phase 5.
- Review existing additive batches separately: `uci_staff_messaging_uc` adds workspace/staff/messaging/UCI tables (budget locks and check FKs); the `uci_staff_messaging_uc` reconciliation also adds previously missing tables/indexes (check uniqueness before any index change); `uci_review_version` and `staff_reset_attempts` add review version and reset attempts (test stale writes, old code with extra columns, and expiry). Use the actual provider filenames and review *every* pending entry. Legacy baseline or unknown histories are a separate migration review, not an assumption of compatibility.
- For a backward-compatible additive change, first revert **application artifact only** via the previous-good marker; leave added tables/columns and post-deploy data intact. Recheck expected release identity, readiness, authorization and rollback-only write probe. MariaDB DDL implicitly commits; failed or partially applied migrations require reviewing actual schema/ledger with DBA. SQLite table rebuilds are outside this approved scope. Do not run blind `migrate resolve`, `db push`, reset or reverse SQL. If previous code is incompatible, stop writes, preserve WAL/binlog and new data, and choose a forward fix or authorized point-in-time restore/switchover with reconciliation. Test the chosen procedure first in staging, including a forced failure and measured recovery time.
- Before production deploy: require reviewed inventory/drift, verified backup/restore, staged upgrade and prior artifact rehearsal, approved window and explicit separate workflow inputs for backup and migration. GitHub approvals do not substitute for these requirements. Inspect every other host-specific entry point before enabling it; do not use retired/older deploy scripts. After approved release, compare actual release ID, migration history, data invariants, readiness, guarded rollback-only write probe and representative workflows. No live release or rollback is verified here.

## Pools, timeouts and monitoring

MariaDB is capped at **5 connections per client/process**, with no minimum idle connections, 3 s connect timeout, 5 s pool acquisition, 15 s statement and 20 s socket deadlines. The Next.js app and messaging process have separate clients; multiply by replicas plus jobs, migrations and operators. Validate connector/version semantics in the target, tune against server limits and observe pool queue/waits, read latency, server slow-query telemetry (redacted), statement/lock timeouts, error rates, and connection count after repeated restarts. Local SQLite uses libSQL and has no MariaDB pool or equivalent server-side statement timeout. `/api/health/ready` queries app tables and an authorized POST writes inside an intentionally rolled-back transaction. It is not an end-to-end workload or failover test; obtain DB-outage, reconnection, load and tuning evidence on the approved deployment topology.
